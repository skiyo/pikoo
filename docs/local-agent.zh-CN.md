# ESP32 本地 Agent

这个开发分支保留原有 GCP 7 模式，另提供 ESP32-S3 发起的原生 GPT‑Live 会话。设备执行家庭工具、保存文字上下文和控制麦克风与播放。Terra、网页搜索和 Decisions 分类由 OpenAI 在同一 Live 连接上运行。远程主机只需要 Mihomo 的转发能力。

## 网络

将 `server/deploy/mihomo-device.yaml.example` 的 listener 和两条规则合入 Mihomo。把专用规则放在宽泛的域名或 MATCH 规则前。使用设备可验证、与主机名匹配的 TLS 证书和专用代理凭证。现有只绑定回环的混合端口可以保留。先在目标版本用 `mihomo -t -f /path/to/config.yaml` 检查配置。设备以 TLS 连接 Mihomo，在 CONNECT 隧道上再次校验 OpenAI TLS，并只在内层发送 OpenAI Bearer。此路径需要 OpenAI 项目有 GPT‑Live 1、Terra、Decisions 和托管搜索权限。

独立部署可以使用 `server/deploy/pikoo-device-proxy.service`，将配置写到 `/etc/mihomo/device.json`，权限设为 0600，然后启用服务的开机启动。示例的证书路径由 Let's Encrypt 管理，`SAFE_PATHS` 允许 Mihomo 读取该目录。配置防火墙 TCP 8443，并确保云防火墙和主机防火墙均持久保存。证书续期的 deploy hook `server/deploy/pikoo-nginx` 会在代理正在运行时重启它读取新证书；短期 IP 证书需要保留现有六小时续期定时器。服务重启会断开会话，设备必须重新连接。

## 设备

1. 构建固件后备份原机 Flash。首次迁移要刷应用和更新后的分区表。表中新增凭证和家庭数据分区，原分区位置不变。不要用本地安装工具把密钥打包进任何 NVS 镜像。
2. 专用凭证分区使用普通 NVS，适用于当前家庭自用部署。OpenAI 密钥与代理凭证通过 USB 写入，后续运行 provision 可以覆盖更新，运行 forget 可以删除。家庭数据导出不包含凭证。
3. 用 ESP-IDF 环境运行 `python tools/local-agent-usb.py --port /dev/cu.usbmodem… provision`。凭证由终端提示输入，写入设备后运行同一工具的 `reboot` 命令重启。重启命令只在已完全静音的待机状态接受。PCM 默认 16 kHz，若目标项目只支持 24 kHz，可通过同一命令重新配置。采音与 AEC 仍保持 16 kHz。首次真机测试前保留旧网关作为回滚路径。
4. `export 备份.json` 导出家庭数据到权限为 0600 的新文件。`import 备份.json` 载入数据，重启后生效。`legacy` 切回原模式并重启。导出包含家庭内容，凭证分区不参与导入导出。导入现有服务端数据时，将已确认的条目映射到下列格式，原始备份在验证条目数前保留。

```json
{"version":1,"shopping":["牛奶"],"todo":["拿快递"],"memory":["家里偏好温水"],"calls":[],"history":[]}
```

每组最多 32 项，每项最多 512 UTF‑8 字节。快照总上限为 24 KiB。设备以双槽提交，最近 32 个写调用 ID 与状态保存在同一快照。短期上下文最多 12 条。背景用户转写只在内存等候分类，未获明确互动判定的内容不保存。清单、显式记忆和上下文独立。设备对确切条目执行删除和修改，清空要求确认。指定网页能否读取取决于 OpenAI 搜索返回的来源。此版不运行后台自动记忆学习，也不做跨设备共享。

## 无声回归

宿主需要 C++17、OpenSSL 开发库、ESP-IDF 源码中的 cJSON，以及 Python 3。macOS 可将 `OPENSSL_PREFIX` 指向 Homebrew 的 OpenSSL。测试只处理固定合成 PCM 和内存帧。

```sh
# ASan/UBSan 和短跑
PIKOO_SANITIZE=1 tools/test-local-agent.sh 15
# 100 次真实 Mihomo TLS / CONNECT / TLS / WS，OpenAI 端为本机假服务
tools/test-local-agent.sh --network --mihomo /path/to/mihomo --cycles 100
# 30 分钟墙钟跑流
tools/test-local-agent.sh 1800 --realtime
# 加速的 8 小时等量 PCM 和双眼帧回放
tools/test-local-agent.sh 28800
# 8 小时墙钟浸泡
tools/test-local-agent.sh 28800 --realtime
```

本机网络测量是 Mihomo 到回环夹具的 TLS、CONNECT 和首 PCM 延迟。桌面网络驱动用系统 TLS，设备的嵌套 mbedTLS 通过 ESP-IDF 交叉编译验证，实际握手峰值需要上板。虚拟播放延迟包含保留的 900 ms 预缓冲。旧链路对照测的是同一 PCM 的旧事件解析和播放入队，远程部署端到端延迟留到实机对照。生产切换必须验证真实出口、证书、模型权限、硬件 AEC 和 Wi‑Fi 后再停旧网关。

## 静默测量记录

Mihomo v1.19.33 与本机 OpenAI 夹具完成 100/100 次双 TLS、CONNECT 和 Live WebSocket 连接。测量覆盖外层及内层证书拒绝、代理 403/407、目的域名与端口拒绝、模拟 API 401/429、代理重启、WebSocket 分片及分片传输中途断线。现有服务端和模拟器 Node 回归为 93/93。

| 回环指标 | P50 | P95 |
| --- | ---: | ---: |
| TCP + 代理 TLS | 1.46 ms | 1.66 ms |
| CONNECT | 0.10 ms | 0.17 ms |
| OpenAI 内层 TLS | 2.34 ms | 2.72 ms |
| 连接开始到首个模拟 PCM | 5.32 ms | 6.07 ms |

加速回放处理 8 小时等量 PCM，执行 100 次本地会话重建，播放欠载为 0，队列峰值 14,720 样本（920 ms），虚拟唤醒到播放 P50/P95 均为 910 ms。最终核心的新路径单包解析、解码和入队 P95 为 2 µs，同进程旧事件格式对照为 2 µs。整场测试约 4.66 CPU 秒，macOS 峰值 RSS 约 3.05 MiB。

另用 16 kHz 初版共用核心完成以下墙钟测试，最终版本的 PCM 路径另以加速回放和 ASan/UBSan 验证。墙钟测试通过内存时钟播放 PCM，不调用麦克风或扬声器。

| 墙钟回放 | 欠载 | 虚拟首声 P95 | CPU 时间 | 峰值 RSS |
| --- | ---: | ---: | ---: | ---: |
| 30 分钟 | 0 | 910 ms | 2.96 s | 2.61 MiB |
| 8 小时 | 0 | 910 ms | 56.76 s | 2.63 MiB |

8 小时进程每分钟采样一次，预热后峰值 RSS 未继续增长。ESP-IDF 5.5.5 构建使用与仓库策略哈希匹配的唤醒模型，6 MiB 应用分区剩余约 57%，静态 DIRAM 用量为 167,163 字节。正式镜像大小与摘要见脱敏验证 JSON。上面的代理延迟与墙钟回放均为桌面测量，板上指标见下一节。


## 2.0.0 实机验证

已备份并校验原机完整 16 MiB Flash；未修改 eFuse。密钥使用可覆盖和删除的普通 NVS。两条原购物条目与五条明确确认的家庭资料已导入，断电/重启读回一致。历史自动记忆中的矛盾称呼保留备份，未转成已确认事实。测试清单和测试记忆已移除。

| 项目 | 观察结果 |
|---|---|
| USB 连续开关 | 100/100，无意外重启 |
| USB 控制线复位 | 20/20，约 2.6 秒恢复诊断 |
| USB 数据 | 22,431 字节快照导入后连续 3 次导出一致；持续连接另测 3 次 |
| 本地凭证替换 | 临时无效密钥进入鉴权错误、上传关闭；覆盖真实密钥后恢复 |
| 真实 API | 本地唤醒、16/24 kHz 问答、清单与显式记忆工具写入、托管搜索已观察成功 |
| 插话 | 原有 -2 dB 音量下清空旧播放，随后 8 秒无复播；后续算术问题回答正确 |
| 隐私 | 静音后 10 秒上传样本计数不增加 |
| I²S | 所观察会话收发错误均为 0 |

原生 USB 失联现象与 [ESP-IDF 上游报告 #18996](https://github.com/espressif/esp-idf/issues/18996) 一致。主机控制台避免打开时改写控制线路，固件启动时重连 USB 外设；随后完成上述 100 次重开和 20 次复位。一次后续 USB 消失由用户确认误拔线，不计为固件故障。

输入转写只在语义明确且出现完整停止/纠正短语时触发清队列，覆盖“不要修改”不误取消和跨片段“停一下”。停止指令按 client_event_id 确认；旧时间线文本被丢弃，新回复根据其时间线恢复，避免吞掉打断后的新回答。相关回归通过 ASan/UBSan。协议依据：[GPT-Live 会话文档](https://developers.openai.com/api/docs/guides/live-conversations)。

七次实机连接观察（含候选版本和 16/24 kHz），TCP P50/P95 为 16/142 ms，代理 TLS 为 1,736/1,785 ms，CONNECT 为 15/25 ms，OpenAI TLS 为 2,222/5,260 ms。样本较少，不能替代 100 次板上连接统计。记录到的六次冷连接首个虚拟硬件播放起点为 7.09–12.93 秒，包含握手、模型启动与预缓冲；不是纯模型响应延迟。内部堆低水位最低 39,828 字节，最大连续块 31,744 字节。待机双眼约 19 FPS，会话中约 8–11 FPS；未测量板上 CPU 百分比。

播放间隔计数曾增加，包含连续流静音和突发间隔，未将其认证为“实机零欠载”。用户曾反馈偶发说话断续，随后接受当前声音并要求停止有声测试；其声学原因尚未确认。静默重放既有收包时间轨迹、播放启动期限、取消与迟到帧测试全部通过，不将这些结果当作新的真人听感验收。桌面零欠载与实机 I²S 零错误分别报告。真实儿童唤醒、装壳声学、家人闲聊误答及 24 小时试用仍须人工验收。

远程 Mihomo 已启用开机启动，8443 已持久写入主机及云防火墙，证书续期 hook 实际重启代理成功。旧远程 Agent 已停止并禁用开机启动；真人清单读取已获用户确认。用户授权静默回归后提交并合入主干，设备保持 MIC OFF，不再运行外放、唤醒或语音测试。完整脱敏数值见 [verification-2.0.0.json](verification-2.0.0.json)。
